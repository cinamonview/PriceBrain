# 11. 테스트 및 품질관리 가이드

## 1. 문서 목적

본 문서는 서비스 개발이 완료된 이후 실제 배포 및 운영 단계로 진입하기 전에 수행해야 하는 테스트와 품질관리 절차를 정의한다.

본 문서에서는 다음 항목을 중심으로 시스템의 안정성을 검증한다.

- Frontend 기능 테스트
- Firebase Authentication 테스트
- Firestore 데이터 테스트
- Firestore Security Rules 테스트 (**Rules SSOT: `docs/05_FIREBASE_DATA_STRUCTURE.md` §6 — 본 문서 §9**)
- 사용자 권한 테스트
- 오류 및 예외 상황 테스트
- 반응형 UI 테스트
- 성능 테스트
- 보안 테스트
- 배포 전 최종 검증
- 배포 후 운영 검증

본 문서의 목적은 단순히 기능이 정상적으로 동작하는지 확인하는 것이 아니라,

> "실제 사용자가 서비스를 이용했을 때 문제가 발생하지 않는가?"

를 검증하는 것이다.

# 2. 테스트 기본 원칙

테스트는 다음 원칙을 기준으로 수행한다.

### 2.1 기능 정상 여부 확인

각 기능이 요구사항에 맞게 동작하는지 확인한다.

예:

- 회원가입이 정상적으로 이루어지는가?
- 로그인이 정상적으로 이루어지는가?
- 로그아웃이 정상적으로 이루어지는가?
- 데이터가 정상적으로 저장되는가?
- 데이터가 정상적으로 조회되는가?
- 사용자가 자신의 데이터를 수정할 수 있는가?

### 2.2 비정상 상황 테스트

정상적인 사용뿐만 아니라 잘못된 입력이나 예외 상황도 테스트한다.

예:

- 빈 입력값
- 잘못된 이메일
- 잘못된 비밀번호
- 존재하지 않는 데이터
- 권한이 없는 사용자의 접근
- 네트워크 오류
- 중복 데이터
- 잘못된 URL 접근

### 2.3 보안 테스트

사용자가 접근해서는 안 되는 데이터에 접근할 수 없는지 확인한다.

특히 Firebase를 사용하는 경우 Firestore Security Rules가 핵심적인 테스트 대상이다.

### 2.4 다양한 환경 테스트

PC 환경뿐만 아니라 모바일 환경에서도 정상적으로 동작하는지 확인한다.

검증 대상:

- Chrome
- Edge
- Safari
- Android
- iOS
- Desktop
- Mobile

9. Firestore Security Rules 테스트

Firebase를 사용하는 서비스에서는 Security Rules 테스트가 매우 중요하다.

**Rules SSOT:** `docs/05_FIREBASE_DATA_STRUCTURE.md` **§6** (본 문서에 Rules 전문 복제 금지)

단순히 Frontend에서 버튼을 숨기는 것만으로는 보안이 확보되지 않는다.
Firestore Emulator + Client SDK로 **05 §6** Rules를 검증한다.

### 9.1 테스트 환경

- Firebase Emulator Suite (Firestore)
- `firestore.rules` = **05 §6**과 동일
- Client SDK (익명·인증 사용자 시뮬레이션)
- Admin SDK는 Rules 우회 — catalog write 테스트는 Admin으로 별도 (**09**)

### 9.2 Catalog read (Client SDK — allow)

**05 §6** catalog collections. 익명 사용자 read **허용** 확인:

| # | Collection / Path |操作 | Expected |
|---|-------------------|------|----------|
| R-01 | `gpu_vendors/{id}` | get | allow |
| R-02 | `gpu_models/{id}` | get | allow |
| R-03 | `products/{id}` | get | allow |
| R-04 | `listings/{id}` | get | allow |
| R-05 | `listings/{id}/price_history/{hid}` | get | allow |
| R-06 | `listings` | query `where product_id == ?` | allow (Index **05 §7**) |
| R-07 | `gpu_families/{id}` | get | allow |
| R-08 | `board_partners/{id}` | get | allow |
| R-09 | `malls/{id}` | get | allow |
| R-10 | `sellers/{id}` | get | allow |

### 9.3 Catalog write (Client SDK — deny)

**05 §6** + **13** MVP. 익명·일반 사용자 Client write **거부**:

| # | Collection / Path |操作 | Expected |
|---|-------------------|------|----------|
| W-01 | `products/{id}` | set / update | deny |
| W-02 | `listings/{id}` | set / update | deny |
| W-03 | `listings/{id}/price_history/{hid}` | set (append) | deny |
| W-04 | `listings/{id}/price_history` | batch append | deny |
| W-05 | `crawl_jobs/{id}` | read / write | deny |
| W-06 | `crawl_logs/{id}` | read / write | deny |
| W-07 | `validation_logs/{id}` | read / write | deny |
| W-08 | `gpu_families/{id}` | set / update | deny |
| W-09 | `board_partners/{id}` | set / update | deny |
| W-10 | `malls/{id}` | set / update | deny |
| W-11 | `sellers/{id}` | set / update | deny |

### 9.4 User data (Phase 2+ — 05 §6 users 규칙)

| # | Path | Auth |操作 | Expected |
|---|------|------|------|----------|
| U-01 | `users/{uidA}` | uidA | read/write own | allow |
| U-02 | `users/{uidA}` | uidB | read | deny |
| U-03 | `users/{uidA}/favorites/{productId}` | uidA | write | allow |
| U-04 | `users/{uidA}/favorites/{productId}` | uidB | write | deny |

### 9.5 Admin SDK write (Rules bypass — 기능 테스트)

Client deny와 별도로 **09 Repository** integration:

| # | 시나리오 | Expected |
|---|----------|----------|
| A-01 | `ProductRepository.upsert` → `products` | success |
| A-02 | `ListingRepository.upsert` → `listings` | success |
| A-03 | price unchanged → `price_history` skip | no new doc |
| A-04 | price changed → `price_history` append | new subcollection doc |
| A-05 | upsert uses `products` not `canonical_products` | path = `products/{id}` |

### 9.6 Pass 기준

- §9.2 전 항목 allow
- §9.3 전 항목 deny (permission-denied)
- §9.5 A-01~A-05 integration pass
- Rules 변경 시 **05 §6** 먼저 갱신 후 본 절 시나리오 재실행

필요한 경우 처리 중에는 버튼을 비활성화한다.

button.disabled = true;

→ 데이터 수정

→ 공개 기능 이용
→ 보호된 페이지 접근

보호된 페이지에 접근할 수 없어야 한다.

      ↓

29. 향후 자동화 테스트

서비스 규모가 커질 경우 수동 테스트만으로 모든 기능을 검증하기 어려워진다.

향후 다음과 같은 자동화 테스트를 도입할 수 있다.

Unit Test

개별 함수나 컴포넌트를 테스트한다.

Integration Test

여러 기능이 정상적으로 연결되는지 테스트한다.

E2E Test

실제 사용자의 행동을 자동으로 재현하여 전체 서비스를 테스트한다.

예:

사이트 접속
→ 로그인
→ 메뉴 클릭
→ 데이터 입력
→ 저장
→ 결과 확인

향후 프로젝트 규모에 따라 적절한 테스트 자동화 도구를 도입한다.

31. 최종 목표

본 테스트 및 품질관리 과정의 최종 목표는 단순히 오류를 찾는 것이 아니다.

사용자가 서비스를 이용할 때

기능이 정상적으로 작동하고
데이터가 안전하게 저장되며
다른 사용자의 데이터에 접근할 수 없고
오류가 발생하더라도 서비스가 안정적으로 대응하며
PC와 모바일에서 편리하게 사용할 수 있는

안정적인 서비스를 제공하는 것이다.

따라서 개발 완료 후 반드시 테스트 → 수정 → 재테스트 과정을 거친 후 Production 환경에 배포한다.
